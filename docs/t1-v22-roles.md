# T1 V2.2 基础角色与组织权限产品方案 V0.2

日期：2026年10月3日  
对应任务：V2.2基础角色与组织权限需求完善  
状态：轻量方案及交互评审稿；不代表生产功能已上线或需求评审已通过。

## 一、范围与基本关系

本期只设三类固定角色：**管理员、投放人员、财务人员**。沿用已有成员协作方案，不建设复杂组织系统，不保留此前预研和Demo中扩展的其他可选角色。

- 登录用户代表具体人员，每个人使用自己的账号，不共用管理员密码。
- 组织是围绕同一广告主的成员集合。本期界面仅管理当前关联的一个广告主，不增加部门层级、多组织或多广告主切换。
- 成员通过已有绑定关系或管理员邀请获得访问资格，再按角色使用功能。同一广告主的成员不按“本人创建”隔离广告和报表。
- 一名成员对应一个角色，一个广告主保留一名管理员。角色只控制T1已开放的能力，不扩大广告主对SSP资源的操作权。
- 移除成员、调整角色和交接管理员均不改变广告归属、余额、投放状态及历史数据。

## 二、三类角色与权限

| 功能 | 管理员 | 投放人员 | 财务人员 |
| --- | --- | --- | --- |
| RTB创建、编辑、启停、归档 | 可以 | 可以 | 不可以 |
| CPD允许修改的创意及版本查看 | 可以 | 可以 | 不可以 |
| 投放详情、效果报表与导出 | 可以 | 可以 | 不可以 |
| 效果报表中的曝光、点击、CTR及RTB消耗 | 可以 | 可以 | 不可以 |
| 账户余额、充值申请、充值记录及凭证 | 可以 | 不可以 | 可以 |
| 财务消耗记录查询及导出 | 可以 | 不可以 | 可以 |
| 邀请、调整角色、移除及管理员交接 | 可以 | 不可以 | 不可以 |
| 本人账号验证、组织关系、帮助及联系运营 | 可以 | 可以 | 可以 |

**区分投放消耗与充值账务：** 投放人员需要通过效果报表查看投放消耗，但不因此获得充值记录、付款凭证和财务管理权限。财务人员在财务页面查询消耗，不通过该页面获得投放编辑或完整效果报表权限。

管理员同样不能修改运营管理的CPD计划、资源排期、价格，也不能自行批准充值到账。暂停、归档、创意审核等继续遵循对应模块原规则。

## 三、存量用户的默认管理员

### 1. 已确认规则

**同一广告主下，最早成功绑定该广告主的用户，默认设为管理员。**

按绑定成功时间比较，不按账号注册时间、提交申请时间、姓名、成员列表顺序或本次登录顺序判断。其他广告主的绑定记录不参与比较；失败、驳回、待审核的绑定申请不算成功绑定。

例如：用户甲先注册，但用户乙先成功绑定这个广告主，则乙为默认管理员。

### 2. 只初始化一次

默认分配在存量迁移时执行一次并保留分配依据。之后已完成管理员交接的，以现任管理员为准；重新登录、刷新或换邮箱都不能恢复成最早绑定用户。已有明确、可核验的管理员交接记录，也不能被本次默认分配覆盖。

管理员不能直接将自己移除或通过普通角色调整取消自己的管理员身份，应先完成交接，避免无人管理或同时出现两名管理员。

### 3. 无法可靠判断时

以下情况标记“管理员待核对”，由运营核验历史绑定记录及账户归属：

- 成功绑定记录缺失、时间无效，无法完整比较。
- 多人最早成功绑定时间相同，现有记录不能证明先后。
- 最早绑定用户已停用、被移除或无法核验有效身份。

不自动把第二个用户、当前登录用户或列表第一行提升为管理员。异常期间不新增成员管理权限，原有投放及历史数据保持不变。运营纠正归属的后台能力不在本次Demo中伪造为已实现。

### 4. 其他存量成员

不增加“待分配角色”，也不把无明确角色的人长期挂在当前成员列表。其他存量成员的角色在迁移时确认；无法确认的单独核验，不擅自赋予投放或财务权限。Demo不再保留旧只读成员样例。

## 四、页面与双向加入流程

### 1. 当前成员

只展示已经成功绑定、具有明确角色的现有成员，列为姓名／T1账号、角色、绑定时间和操作。删除没有区分价值的“已加入”状态列。管理员看全体成员；投放和财务人员仅看本人关系、管理员联系信息及固定权限说明。

管理员页面分为当前成员、邀请记录、申请记录、邀请码及操作记录。未加入的人只出现在邀请／申请记录中；已移除的人退出当前成员列表，历史操作保留。

### 2. 管理员主动邀请

管理员填写对方已有的T1账号邮箱，并选择投放人员或财务人员。不另填对方姓名，以账号资料为准，不通过邀请直接授予管理员身份。

发送前校验账号存在、可用、不是本人、尚未绑定其他广告主，也不是当前成员；同一用户已有有效邀请或待审批申请时，提示先处理已有记录。

邀请发送到对方T1账号的小铃铛，展示广告主、邀请人、拟加入角色和有效期。对方选择接受或拒绝：

- 接受时再次校验绑定资格，通过才绑定并按邀请角色成为成员，无需管理员二次审批。
- 拒绝不绑定、不获得任何广告主业务权限，管理员收到结果。
- 管理员可撤销尚未接受的邀请；撤销、过期或已处理的邀请不能重复接受。
- 同一账号在等待期间已绑定其他广告主时，本邀请失效并说明原因，不覆盖原绑定。

邀请记录状态：待接受、已接受、已拒绝、已撤销、已过期、已失效。再次邀请通过新建邀请发起，旧失效记录不恢复为可接受。

### 3. 用户通过邀请码申请

未绑定的T1用户在自己的广告主关联页或首页输入邀请码，校验有效性后展示广告主名称和ID，由用户核对，再选择希望加入的角色并提交申请。

邀请码仅用于定位广告主和提交申请，不凭码直接绑定或获取权限。不存在、过期、停用的邀请码明确报错；提交时重新校验邀请码，避免校验后已失效仍可提交。

管理员在小铃铛收到申请，查看申请账号、期望角色，决定通过或不通过：

- 通过前必须确认最终角色，可以将申请人的期望角色调整为投放人员或财务人员；用户获得的是管理员确认的角色，不自行提权。
- 通过时再次校验申请人仍未绑定其他广告主，符合条件才完成绑定并通知申请人。
- 不通过需填写原因，申请人收到结果，仍未绑定且无业务权限。
- 申请人可撤销待审批申请；撤销后管理员旧页面不能继续批准。
- 同一用户仅保留一条有效的待审批申请；存在待处理邀请时先处理邀请，避免同一人同时重复申请和接受。

申请记录状态：待审批、已通过、未通过、已撤销、已失效。已通过时展示实际角色，若与申请不同，同时保留原申请角色供核对。

已绑定一个广告主的人，不能申请或接受绑定另一个广告主。加入流程最终生效时再次检查，以当时的绑定状态为准；重复点击或两个流程相继处理，不能产生重复成员或第二个绑定。

### 4. 未绑定用户的页面

未绑定不是第四种角色，而是账号尚未建立有效的成员关系。用户能登录、查看本人铃铛、邀请和申请进度、接受／拒绝邀请、提交／撤销申请；不能查看目标广告主的投放、报表、余额或财务信息。

页面保留账号验证、帮助和联系运营，不以隐藏整个铃铛的方式限制未绑定用户。通知已读不等于接受邀请、批准申请或业务完成。接收用户只能处理自己的邀请和申请，管理员只能处理本广告主的记录。

已移除用户的登录账号仍保留，展示访问权限已收回；不再拥有原广告主的数据权限，可按规则重新申请。已绑定其他广告主的冲突样例仅展示关联状态及本次记录，不展示其他广告主业务数据。

### 5. 成员角色、移除和交接

管理员可调整普通成员为投放人员或财务人员，保存后立即按新权限生效，不叠加旧权限。移除前明确对象和影响；移除不注销T1账号，不删除其广告、财务及操作历史，也不停止现有广告。

管理员不能直接移除自己或通过普通角色修改取消自身管理员身份。交接目标必须是已加入、有效的投放或财务成员；原管理员选择自己交接后的投放／财务角色，明确确认后立即完成交接，不新增审批链。取消不改变角色。确认成功后同时更新双方权限，只有一名管理员，刷新不会恢复原管理员。

新成员通过邀请或申请加入，不再次触发存量管理员初始化。管理员无法登录或归属不明，联系运营核验，不由普通成员抢占身份。

### 6. 邀请码与期限

管理员可查看、复制、生成和停用成员申请邀请码。邀请码停用／过期后不能用于新的提交，但不自动否定此前已有效提交的申请；管理员仍按申请人的当前资格审批。

邀请有效期及新生成邀请码有效期暂沿用7天作为演示参数，正式期限待评审。邀请及审批全部在T1站内完成，不将邮件回执当作加入前提。本次不接真实账号查询、消息推送或服务端绑定。

## 五、与首页、通知、账号流程的关系

- 首页仍沿用已确认的结构。管理员和投放人员按自身可访问范围查看投放内容；充值及资金待办仅对有财务权限的成员提供操作入口。财务人员沿用资金工作台。
- 无操作权限时不提供可执行按钮；直接访问也应明确拒绝，不能通过通知、报表或帮助页绕过。
- 组织成员变更事件按现有通知方案通知管理员，角色变化后的界面同步更新；具体接收和保留规则与首页通知方案共同评审，不在本模块另建消息中心。
- 本人邮箱验证、找回密码和存量账号重置不改变原用户身份及成员关系；更换登录邮箱不能重新参与默认管理员排名。
- 不新增工作空间切换、逐计划授权、自定义角色、多级部门或额外审批流程。

## 六、角色页面与Mock场景

评审页顶部提供“用户视角”和“场景筛选”，仅评审模式显示，不是正式产品的工作空间切换。

- 管理员：全体成员、邀请、申请、邀请码、操作记录，以及本期投放和财务。
- 投放人员：本人关系、投放页面与效果报表，无财务及成员管理入口。
- 财务人员：本人关系、资金工作台、充值及财务记录，不开放投放和完整效果报表。
- 未绑定用户：本人邀请、申请、铃铛及邀请码入口；无广告主业务数据。
- 已移除／已绑定其他广告主：分别演示权限回收和绑定冲突。

切换用户保留当前操作结果，可连续演示管理员发送、对方接受、管理员查看新成员。切换场景重置成员、邀请和申请的Mock；保留广告、余额、充值、报表及财务操作记录。刷新保留当前用户、成员关系、角色和处理结果。

31个场景覆盖：三角色及未绑定页面；发出邀请、待接受、接受成功、拒绝、撤销、过期、接受前已绑定他人；新申请、待审批、管理员审批、通过及角色调整、未通过、撤销、审批前已绑定他人；无效／过期／停用邀请码；重复邀请、账号不存在、邀请自己、已经是成员、已经绑定他人；移除、管理员交接、无权限、邀请码管理、无邀请申请的空态。

测试账号及邀请码仅在评审工具说明中展示，产品页面不混入内部测试按钮。普通广告主视角不显示任何用户或场景筛选。

## 七、验收与系统依赖

重点检查：

1. 角色与加入状态分离，成员列表无“待分配角色”和重复“已加入”列。
2. 发邀请、提交申请都不直接增加成员；最终接受或审批通过后才生效。
3. 绑定前后重复校验，禁止一个账号绑定两个广告主；已失效操作不能继续提交。
4. 通知按本人／本广告主管理员展示，未绑定用户可见自己的消息但不能越权查看数据。
5. 角色调整、交接和移除后旧权限失效；业务数据保留。
6. 新旧Demo代码、存储和冻结基线隔离。

正式实现仍需核实T1账号查询、历史绑定记录与原权限来源、站内通知、邀请码归属和期限、服务端统一绑定校验以及权限变更对已登录会话的生效方式。不得只用前端隐藏按钮代替鉴权。

本稿替代V0.1中的邮件邀请与待分配过渡设计。已确认的最早成功绑定者默认管理员规则不变。当前交付仍是产品方案及交互Mock，未变更真实用户、绑定、权限或资金。
